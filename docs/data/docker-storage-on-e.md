PostgreSQL retains its Linux named volume, `backtest-infra_backtest_postgres`, mounted at `/var/lib/postgresql`; the project connection remains on localhost port 54328.

The 2026-10-09 migration preserved all existing containers, volumes and images. The stopped source and E cold backup matched SHA-256 for both VHDX files before native migration. Verification records are under `artifacts/storage-migration/`: `backup-verification.json`, `native-move.json`, `after-native-inventory.json`, `after-sql.json` and `operation.json`. The recoverable cold backup is on E at `E:\DockerData\storage-migration-20261009`. Do not delete the active E disk or the only recoverable backup as part of routine cleanup.

Docker Desktop 4.74.0 initially failed to start because inaccessible, zero-byte AF_UNIX socket reparse points remained in its Secrets Engine and Inference runtime directories. Only verified Docker processes were stopped; directories containing only the affected sockets were renamed aside, preserving their contents. Factory reset was not used. The engine then started successfully and completed the native move. This behavior is documented in Docker's [startup socket issue](https://github.com/docker/desktop-feedback/issues/460).

## PostgreSQL child-process recovery on 2026-10-10

PostgreSQL later reinitialized without a Docker container restart when an untracked child exited with code 2. An isolated reproduction using the exact production image, no network, no persisted volume and tmpfs storage reproduced this behavior with PostgreSQL as PID 1. Adding Docker's [init process](https://docs.docker.com/reference/compose-file/services/#init) reaped the orphan without reinitializing PostgreSQL. The actual historical child's executable was not logged, so the reproduction establishes the failure path, not the identity of that process.

On 2026-10-11 the Docker backend was absent and all eleven active collection/enrichment groups ended with DB transport failures. The backend log ended abruptly at 00:13:49 KST; a sandbox service restart at 00:14:12 and WSL virtual-port removal at 00:15:08 were contemporaneous observations, not proof of the initiating cause. There was no observed Docker panic, orderly quit, disk-full or OOM evidence. The original PostgreSQL container had `restart=no`, so it remained exited after the engine returned. Recovery launched Docker Desktop through detached WMI, retained the exact container/image/volume/port, and changed only its restart policy to `unless-stopped` (also saved in Compose). PostgreSQL performs ordinary WAL crash recovery before any collector is resumed. Never reset WAL or recreate the volume to shorten this wait.

It preserves metadata/progress, registers each successful detached launch immediately, keeps KIS and Alpaca raw source lanes separate and waits for the clean pipeline before the metric dependency. Completed index/recovery jobs and the intentionally stopped extra release are history and are not relaunched. Driver connection establishment timeout variants now use the existing finite DB recovery policy; query timeout, authentication failures, failed sessions and unknown errors retain their prior behavior.

The later explicit request to keep collecting across budget boundaries is implemented by the singleton `artifacts/continuous/manager.py`. It does not weaken fencing or modify source jobs/data/checkpoints. Credentials/permissions, disk guards, unidentified failures and launch ambiguity remain explicit action states. The container was recreated with the same image, named volume, port and database system identifier. All pre-existing release seals and target-manifest hashes matched before/after.

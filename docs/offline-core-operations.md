# Continuous offline acquisition

The `Offline core refresh` workflow collects US daily price bars and new SEC and OpenDART periodic filings independently of local historical collectors. Its immutable runtime and original target catalog are hash-pinned release assets. Existing KRX collection and local collectors keep their own source and checkpoints.

The source split is recorded in [the ownership specification](superpowers/specs/2026-10-12-source-ownership.md). Local KIS domestic/overseas, KIND/FSC, supplemental sources, Alpaca supplier adjusted prices and VWAP inputs keep their current authority. Local raw Alpaca and SEC/OpenDART unfinished historical work continues through 2026-10-07; `core-forward-v1` owns new forward raw-price and filing discovery from 2026-10-08. Local PIT, coverage and metric audits remain local. KRX retains its separate remote historical queue and local SQL receiver.

An explicitly bound `artifacts/source-ownership.json` fences new completed-pass local Alpaca/SEC/OpenDART refresh planning. It does not stop a collector or alter source rows. Already planned jobs, pending/retry queues and frozen planning cursors drain first. Remote downtime preserves the fence rather than starting a second owner. Malformed bindings wait for operator review; absence of the opt-in file preserves standalone local behavior.

Runtime v5 bounds newly created fourteen-day price correction windows at the forward start and uses the shared 09:00 Seoul / 06:00 New York project gates. Existing correction cycles, anchors, pagination cursors and historical gap retries retain their original scope, even when a legacy cycle records a failure after upgrade. These legacy overlaps are visible retained work, not new duplicate planning. Financial discovery ownership follows the filing date; an upstream response can contain older accounting periods. Weekday scheduling remains an approximation, not an official exchange calendar.

Each successful run publishes hashed capture bundles, a resumable source checkpoint, and a chained commit manifest as a GitHub Release. Published data releases have no application age expiry. Failed or partial draft releases are not imported. Prices preserve source response bytes; financial captures contain typed numeric extraction evidence and the original response hash. Credentials stay in GitHub Actions secrets.

The target denominator remains the original 17,758 securities. A source watermark means that discovery or traversal was attempted; it does not certify complete market data. Empty price windows retain six-hour retries. Recent fourteen-day price corrections run once per completed weekday. Deferred financial reports remain in the checkpoint for later extraction retries.

Denied SEC archive/index access switches to a resumable scan of all 6,026 target issuers and exact-accession companyfacts evidence. API taxonomy/context is explicitly separate from XML context and remains unqualified. Rejected or oversized OpenDART XBRL keeps its safety bounds and falls back to structured figures only when receipt, corporation, year, report code and financial scope match. Financial retry queues reserve three fresh turns per due retry so old unsupported reports cannot starve current filings.

Source row anomalies and partial financial extraction are retained with validation evidence and incomplete flags; they do not promote unsupported figures or block every later capture. Supplier ticker case-fold collisions are isolated and the remaining exact bulk response is fetched again. Per-run capture metadata is bounded before publication, with a rejected step restored for the next run.

Local login synchronization validates catalog, hashes and the release chain, then resolves native issuer/security identities and commits per-capture SQL receipts. SQL receipts are authoritative after a database restoration; a disk acknowledgment is only a cache. Repeated synchronization does not duplicate captures. The new windowless login task is `BacktestInfra-OfflineCoreSync`, polling every five minutes and retrying temporary connectivity or database outages.

Local SQL import and remote provider health are reported separately. A hash-bound snapshot identifies provider authentication or policy failures requiring action even during old-release catch-up; capacity and network deferrals remain visible as retry status. Large offline backlogs can take time to import while existing collectors use the same local disk.

During replay, progress is written before each release and after every hundred committed captures. It records the current process identity and SQL counters. Provider health remains pending until the bound checkpoint is verified, and any final provider attention state remains visible.

The workflow uses standard public-repository hosted runners with a two-hour job bound, a ninety-minute acquisition budget and export margin. Source budgets reserve separate local and hosted slices before acquisition. OpenDART reservations remain charged conservatively for twenty-six hours, including failed runs. No paid runner or paid storage service is configured.

Service limits still apply. GitHub may delay or drop scheduled runs, public scheduled workflows can be disabled after sixty days without repository activity, and release assets must remain below platform limits. The application splits assets at 512 MiB and updates a useful committed source index after successful capture publication. It has no fixed thirty-day or ninety-day retention limit, but cannot promise unlimited capacity or a scheduler availability guarantee. Re-enabling a disabled workflow resumes from its last committed checkpoint.

Repository activity also survives acquisition failures: an `always()` job commits actual run/workflow health after each permitted core attempt. A separate weekly `Collection maintenance` workflow performs the same check without provider credentials or SQL access. Its useful health commits maintain ordinary repository activity independently of new source captures. The maintenance permission to enable Actions is scoped to its own jobs; it recovers only the two known collection workflows in `disabled_inactivity`, with all relevant operator/budget/handoff/public-data gates satisfied. Manual stops and disabled operator flags are preserved. GitHub outages, disabled Actions and unavailable authorization remain external limits; a workflow already disabled cannot wake itself without another active or external runner.

The weekly check runs Mondays at 08:31 UTC (17:31 Asia/Seoul). Core acquisition retains its original two-hour cadence and ninety-minute budget. The public `data/offline/collection-health.json` stores safe calling-run identities, workflow states, observed native schedule events and the last data release; it contains no arbitrary provider response or credentials. Writes retry at most four times against the current file SHA and preserve unrelated repository files.

Operations require `OFFLINE_CORE_ENABLED` and `OFFLINE_QUOTA_PARTITIONS_READY` repository variables, provider secrets, and private `OFFLINE_CORE_CONFIGURATION` binding catalog/runtime tags and hashes. Runtime upgrades publish a new immutable runtime release and update that configuration only after verification.

The reviewed public runtime-only pin in `scripts/offline-runtime.json` preserves every private catalog, stream, credential and provider gate. Current runtime v8 rebuilds from the immutable v6 archive with `python scripts/build_offline_runtime.py --base <v6-runtime.zip> --output <new-runtime.zip>`. The checked-in recovery source patch (`offline-runtime-v7.patch`) and the two current publication helpers are its complete changes. The launcher verifies the exact runtime ZIP hash before installing it. Historical v6 rebuild instructions and helper bytes remain available at commit `291fe8b0a804500e92b06cb8cb9517a9de5043d8`.

Publication verifies the original draft identity and each existing asset's size and SHA-256, uploads only missing matching bytes, and verifies the complete release before publication. Conflicting drafts remain intact for operator recovery. Transient reads retry at most four times; ambiguous upload, publication and index/health writes read the server state before any retry. Safe errors retain HTTP status and operation without arbitrary stderr, credentials or provider responses. Existing published generations remain immutable.

## Automatic publication recovery (runtime v8)

The publisher saves an exact compressed `pending.zip` containing only this run's state, capture delta and commit manifest before beginning canonical publication. This is not a SQL database, historical database export or second permanent data store. Its unpublished `offline-pending-<stream>-<sequence>-<commit-hash>` Release binds catalog, stream, sequence, original manifest SHA-256 and package SHA-256. The complete uploaded package is verified before the canonical release can be created. Draft storage does not create another published tag or an extra verification workflow.

Every invocation recovers these saved transactions before loading provider credentials or reserving provider credits. It reuses the original manifest bytes and previously uploaded canonical assets, then repairs a lagging source index. A recovered invocation performs no new acquisition. Hash conflicts, unsupported packages and ambiguous predecessor chains stop with all evidence preserved. An unresolved canonical draft blocks fresh collection instead of collecting a conflicting replacement.

Only after canonical membership, file digests and the committed index have been verified does acknowledgement delete that transaction's owned unpublished staging Release. Published data releases are never removed. The compressed local pending package remains available until acknowledgement. A failed first upload additionally has a 90-day Actions artifact fallback; restoration accepts only the exact hash-bound package from the trusted core workflow on main, with matching repository/run provenance. The primary staging Release has no application age expiry. Neither path can guarantee persistence if every available storage endpoint remains unavailable before the first successful save, or if operators delete the saved inputs.

Transient HTTP failures and known transport errors are reported as `deferred` and resume on the existing schedule. Collection health records that outcome instead of inventing success. Authentication failures, unclassified CLI/configuration errors, corrupt bytes and conflicting data remain actionable failures. Server Retry-After is honored within the bounded wait; a rate-limited 403 is distinguished from an authorization denial. Release inventory is fetched once per transport invocation, updated from verified mutations, and independently refreshed on a new invocation or ambiguous creation. Provider execution time begins after setup, recovery and credit reservation; the existing provider quota and maximum batch duration remain enforced.

The 101 recovery input measured 49,226,972 bytes for the original state/archive/manifest and 4,584,350 bytes (about 4.4 MiB) for the compressed pending package. Compression took 0.363 seconds in one local check on 2026-10-31 Asia/Seoul; this is a sample, not a throughput guarantee. Successful acknowledgement removes the temporary remote duplicate.

`Offline publication recovery verification` runs focused public and extracted-runtime regressions on relevant main changes. It rebuilds the approved ZIP on Linux and checks its pinned hash without provider secrets or a database service. The suite covers exhausted upload retries followed by restart, missing commit, accepted writes with lost responses, index failure after publication, tampered ZIP members, fallback provenance, rate limits and refusal to overwrite conflicting generations. For a live isolated proof, use `scripts/verify_offline_recovery.py` in its `interrupt`, `recover` and `cleanup` phases with a unique canary key. It injects persistent 503 failures only into the test stream's manifest upload; a separate process restores the exact original capture without provider or SQL calls. The canary completed this sequence with unchanged original asset IDs/digests, then removed only its own test Release and tag.

The first Linux CI run also exposed v7's rejection of digits in workflow output keys such as `pending_sha256`; local tests had no `GITHUB_OUTPUT`. v8 validates outputs even without that environment and validates the complete output record before writing any field. Its fallback reader can recover v7's correctly saved package with an empty hash suffix only after the same full workflow provenance, artifact digest, package schema, catalog and commit validation. The invalid output did not alter a published predecessor or discard the saved delta.

The focused suite passed 168 unit tests and 12 isolated PostgreSQL tests.
